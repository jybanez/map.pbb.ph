## Permission path and Chromium evidence

PBB detects the API, rather than assuming Android lacks it. `assets/app.js` onLocate calls direction.request(true) synchronously before location.request(true). `assets/heading.js` calls the API with the DeviceOrientationEvent receiver and true argument before awaiting. Initialization request(false) intentionally does not call an exposed permission API. Diagnostics opens without requesting it. Grant activates listeners; denial/error remains neutral and Locate can retry. A loading direction module warns to retry; duplicate pending calls are ignored.

Current Chromium main, inspected2026-10-10, declares requestPermission in [DeviceOrientationEvent IDL](https://chromium.googlesource.com/chromium/src/+/main/third_party/blink/renderer/modules/device_orientation/device_orientation_event.idl), marks DeviceOrientationRequestPermission stable in [runtime features](https://chromium.googlesource.com/chromium/src/+/main/third_party/blink/renderer/platform/runtime_enabled_features.json5), and routes through [event implementation](https://chromium.googlesource.com/chromium/src/+/main/third_party/blink/renderer/modules/device_orientation/device_orientation_event.cc) to [controller SENSORS permission](https://chromium.googlesource.com/chromium/src/+/main/third_party/blink/renderer/modules/device_orientation/device_orientation_controller.cc). That implementation's signature has no absolute argument; extra JavaScript arguments are ignored there. The [W3C draft](https://www.w3.org/TR/orientation-event/) specifies an absolute permission parameter including magnetometer permission. Passing true supports that API shape; it does not prove exact-build behavior or usable north data. Main source is supporting plausibility, not a version154 source certification or proof of why the owner's snapshot had not activated permission.

The demo uses requestPermission() without an argument and deviceorientation tilt. PBB requests its direction permission from Locate and requires its supported north-reference stream. This comparison found no demonstrated app permission-call defect. The browser fixture uses an Android154 identity with an exposed mocked permission API: no call on load/diagnostics, direct trusted Locate call with active user activation and correct binding, denial then grant retry, active listener after grant, and separate missing-altitude neutral output. Evidence: scripts/verify-android-direction-permission.js, docs/evidence/android-direction-permission.txt. This verifies application wiring, not the phone's actual permission grant. ## Scientific and product distinction

Geolocation altitude and altitudeAccuracy may legally be null under [W3C Geolocation](https://www.w3.org/TR/geolocation/). The existing requirement for altitude accuracy ≤100m is PBB's accepted policy, not a browser guarantee. WMM accepts an evaluation height relative to WGS84; its [documentation](https://www.ncei.noaa.gov/products/world-magnetic-model) explains the altitude reference. Missing GPS altitude must not be relabeled as measured zero, sea level, terrain height or WGS84 height.

I evaluated the pinned local WMM at a synthetic Cebu reference (10.3157,123.8854), date2026-10-10, across explicitly chosen model heights. These are sensitivity probes, not owner location/height. At0m declination is−2.06172°; at3km it is−2.05833°, a0.00339° change; at100km it is−1.95272°, a0.10900° change from0m. The [NOAA surface uncertainty formula](https://www.ncei.noaa.gov/products/world-magnetic-model/accuracy-limitations-error-model), evaluated at the0m horizontal field, is approximately0.294° one standard deviation. This is not a confidence bound for the browser compass: local anomalies/interference and unexposed Android calibration remain additional uncertainties. These samples show weak height sensitivity here, not a worldwide guarantee or known height interval for the phone. Computation: docs/evidence/altitude-sensitivity-cebu.json.

## Recommendation for owner review

Retain the existing geographic marker contract for now and complete the permission observation. If missing altitude persists, recommend an explicitly selected **approximate geographic direction** mode for ordinary handheld map use, with a visible approximate label and documented model-reference-height policy, only after owner approval and validation of its supported region/error budget. Evaluate WMM at an explicit reference surface, retaining actual location.altitude=null and a distinct correction provenance; never insert a fabricated altitude into the location record. This changes the accepted requirement that only measured, accurate altitude can enable the arrow. The owner must accept that approximate field correction is not certified navigation accuracy, that local/sensor errors can dominate, and that near-pole/caution/date/source/freshness/attitude checks still apply. Before implementation, specify supported region, sensitivity/error threshold and behavior outside it; Cebu-only sensitivity evidence is insufficient for global deployment. No such mode has been implemented or enabled.

Alternatives: keep strict neutral output with clear altitude reason (preserves current contract, leaves this phone without a cue); or provide a separate explicitly labeled magnetic compass indicator when magnetic readings are valid (does not require WMM altitude, but it must not be presented as a geographic map arrow because magnetic and geographic north differ). Terrain elevation requires validated vertical-datum conversion and uncertainty; it cannot silently substitute for GPS ellipsoid altitude. Do not treat relative cube tilt as a directional fallback.

The proposed approximate mode is a reviewable product/scientific-policy decision, not an automatic permission to change gates. Physical success remains unconfirmed.
