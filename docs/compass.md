# Device direction

Task176 revision `20261010-compass1` uses the accepted Helper0.21.281 complete person renderer's `headingDegrees`/`updateHeading()` API. The marker's optional gold base cue represents the horizontal direction of the top of the visible screen, clockwise from geographic north. Map bearing and pitch are renderer inputs and do not change that geographic heading. GPS course is never used as facing direction. Physical calibration and real phone/browser tests remain unverified.

## Reference adapters

[Apple documents webkitCompassHeading](https://developer.apple.com/documentation/webkitjs/deviceorientationevent/1804777-webkitcompassheading) relative to magnetic north. Require finite heading0–<360 and compass accuracy0–20 degrees; negative accuracy is rejected. It uses the `deviceorientation` event. No inference of true north from `absolute` is made.

Chromium Android is selected only for an Android Chrome user agent, excluding WebView, SamsungBrowser, Edge and Opera. Require `deviceorientationabsolute`, `absolute===true`, and finite alpha0–<360. The [Chromium Android provider](https://chromium.googlesource.com/chromium/src/+/main/services/device/generic_sensor/platform_sensor_provider_android.cc) selects native rotation-vector quaternion→Euler or accelerometer/magnetometer fusion. [PlatformSensor.java](https://chromium.googlesource.com/chromium/src/+/main/services/device/generic_sensor/android/java/src/org/chromium/device/sensors/PlatformSensor.java) maps absolute quaternion to Android TYPE_ROTATION_VECTOR. [Android SensorManager](https://developer.android.com/reference/android/hardware/SensorManager#getRotationMatrix(float%5B%5D,%20float%5B%5D,%20float%5B%5D,%20float%5B%5D)) documents magnetic-north ENU axes; the platform inference is thus magnetic, not geographic. Normalize natural-screen +Y heading as -alpha. Android events do not expose a reliable compass accuracy value: this adapter cannot certify calibration or local interference. Reviewed upstream provider paths support this assumption; emulated events are not physical Chrome sensor verification. UA identification is compatibility scoping, not authentication. Platform changes need renewed validation.

Other absolute/relative Euler readings have unknown north reference and show a neutral marker. The pure conversion function also accepts an explicitly established geographic reference without declination, but no current browser adapter claims that reference. It never double-corrects it.

## Attitude, screen and lifecycle

Use [W3C device axes/Euler Rz Rx Ry](https://www.w3.org/TR/orientation-event/) and [screen orientation angle](https://www.w3.org/TR/screen-orientation/). Direction means screen top, not rear camera or walking direction. Project the screen-top vector `(sin(screenAngle),cos(screenAngle),0)` to horizontal coordinates. Vendor heading supplies natural +Y yaw. Require beta/gamma within ±60°, quarter-turn screen angles, and horizontal projected norm>=0.3; upright/inverted/ambiguous attitudes stay neutral. ScreenOrientation.angle preferred, numeric legacy window.orientation fallback, otherwise unknown. On orientation change clear the cue and wait for a fresh reading.

Shortest-arc exponential smoothing uses a180ms time constant; first reading after invalid/stale state snaps. Sensor cue expires after2s with no valid sample. Location must be at most60s old, using the preserved GeolocationPosition timestamp when available; cached Locate cannot extend it. Reject timestamps over1s in the future. Hidden page removes sensor listener and clears cue; resume reinstalls one listener only if previously enabled. Pending permission has generation/disposal guards. Denial/rejection is independently retryable through Locate, with canonical toast feedback, and never disables location. Destroy removes listeners/timers. Location errors clear direction while the last location marker can remain.

Where requestPermission is required, startup never calls it. Locate calls it directly from the user's gesture; duplicate pending calls are ignored. On platforms without that method, a passive listener can start without a scripted permission request, subject to browser site sensor policy. Optional model/sensor modules load asynchronously; failed or blocked loading leaves map/location usable and neutral. No extra custom UI component is introduced.

## Local WMM2025

Locally vendored Apache-2.0 [naturalatlas/geomagnetism](https://github.com/naturalatlas/geomagnetism/tree/5cf5cba40d8cadf4220734296bbfe4a7f4351be6), commit `5cf5cba40d8cadf4220734296bbfe4a7f4351be6`, version0.2.0, with LICENSE, NOTICE and source/hash provenance. PBB converts CommonJS to browser ESM and fixes UTC leap-year fractional dates and zero latitude/longitude handling. Official epoch bounds override upstream release-day bounds.

[NOAA WMM2025](https://www.ncei.noaa.gov/products/world-magnetic-model) coefficient archive WMM2025COF.zip is pinned locally. All90 coefficient rows match the port's WMM2025 data exactly. Coefficients/US Government material attribution is retained in NOTICE. No model/correction request leaves the device, and position/sensor values are never persisted by the application.

Inputs: geodetic latitude[-90,90], longitude[-180,180] degrees; WGS84 ellipsoid altitude in metres, internally converted once to kilometres; UTC date from2025-01-01 inclusive to2030-01-01 exclusive. App requires supplied finite ellipsoid altitude[-1000,100000] metres and altitudeAccuracy0–100m, horizontal accuracy<=1000m. Missing altitude is unsupported, never silently treated as sea level or terrain height. Correction uses east-positive declination: geographic heading = magnetic heading + declination, normalized0–360. Model date expiry and invalid inputs yield neutral. Reject NOAA caution/blackout zones H<6000nT.

WMM models the broad internal field, not sensor calibration, nearby metal, crustal anomalies or storms. [NOAA limits](https://www.ncei.noaa.gov/products/world-magnetic-model/accuracy-limitations-error-model) document these limitations and non-navigable polar zones. The app does not certify compass precision, ground/sea-level classification or geomagnetic storm conditions. Real-device review must check permissions, magnetic interference/calibration, portrait/landscape/tilt, OS/browser reference assumptions and practical heading accuracy.
